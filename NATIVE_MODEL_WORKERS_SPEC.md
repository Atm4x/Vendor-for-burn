# Единый контракт нативных inference worker

Статус: спецификация к реализации. Эталон жизненного цикла — [RVC worker из PR #2, `fd6b1a9b`](https://github.com/Atm4x/Vendor-for-burn/blob/fd6b1a9b90b48ab50990527ec73b585b538be39b/models/tts-with-rvc-rs/IPC_STDIO_WORKER.md). Перенос охватывает нативные порты RVC, GigaAM, Beat This!, Fish Speech, F5‑TTS и Dettato. Для последующих моделей применяется тот же контракт. SubRoformer остаётся Python-проектом и потребует отдельного решения о переносе.

## 1. Граница между Core и worker

- **Core** выбирает установленную ревизию, вариант исполнения, устройство и профиль. Core управляет установкой, проверкой пакета, процессом, каталогами обмена, очередью, таймаутами и восстановлением. GUI получает статусы и возможности через типизированную модель представления Core.
- **Worker** загружает явно переданные артефакты, прогревает выбранную модель и выполняет запросы. Один процесс держит одну активную конфигурацию модели и одно выбранное устройство. Общие части модели могут оставаться в памяти при смене профиля.
- **Модельный адаптер** владеет типизированными входами и результатами, форматами весов, препроцессингом и постпроцессингом. Протокол и управление процессом следует переиспользовать между worker. Существующий CLI и IPC уже опубликованных worker сохраняют совместимость.

## 2. Запуск и выбор устройства

1. Worker принимает `--ipc-stdio`, явный вариант исполнения и абсолютные пути к входному и выходному каталогам и ко всем обязательным файлам модели. Роли артефактов задаёт модельный адаптер. Имя файла и рабочая директория процесса не участвуют в выборе модели. Опциональные артефакты объявляются явно.
2. Вариант исполнения фиксирует собранный backend и режим точности. Пакет объявляет фактически собранные варианты. Недоступный, несовместимый или неподдерживаемый вариант возвращает ошибку без автоматической смены backend, устройства или точности. Стратегии ядра внутри одного варианта регулирует сам движок.
3. Для GPU поддерживаемый вариант принимает физический селектор в формате RVC, PCI-адрес или Windows LUID. При переданном селекторе запускается только указанный адаптер. Если селектор не задан, применяется документированное правило backend. `status` сообщает выбранный backend и доступный физический идентификатор. Изменение backend или устройства требует запуска нового процесса.
4. В Windows внешние DLL можно закрепить абсолютными путями. Worker загружает закреплённые DLL до инициализации ускорителя, проверяет фактические пути и держит библиотеки до выхода. Каталог поиска и закреплённая библиотека — два разных параметра. Транзитивная DLL считается закреплённой только при отдельной проверке её пути. CPU-пакеты могут объявлять свои библиотеки, например SoXR у Beat This.
5. Пакет сохраняет офлайн-запуск. Worker получает файлы от хоста и возвращает конкретную ошибку при недостающем или несовместимом артефакте.

## 3. IPC и жизненный цикл

Транспорт v1 — UTF‑8 JSON Lines через stdin/stdout. Запрос состоит из `version`, UUID `id`, `command` и объекта `payload`. Ответ сохраняет `version` и `id`, поле `ok` и пару `result` / `error` по схеме RVC. Диагностика пишется в stderr. Лимит кадра v1 — 1 МиБ. Тип результата и его версия задаются контрактом сервиса отдельно от версии транспортного конверта.

| Команда | Поведение |
| --- | --- |
| `capabilities` | Доступна до загрузки. Объявляет сервис, версию его контракта, команды расширения, варианты исполнения, форматы и пределы размеров. |
| `load` | Из `started` загружает переданный набор артефактов и переводит процесс в `loaded`. При ошибке частично загруженная модель не публикуется. |
| `warmup` | Готовит активную конфигурацию и после завершения работы на устройстве переводит `loaded` в `ready`. |
| `status` | Возвращает `started`, `loaded` или `ready`, фактический вариант и активную конфигурацию. |
| `infer` | Требует `ready`. Принимает вход сервиса и возвращает его типизированный результат. Повторные запросы используют те же веса. |
| `unload` | Освобождает модель и зависимые от неё кэши, переводит процесс в `started`. |
| `shutdown` | Возвращает ответ и завершает процесс. EOF также завершает процесс. |

Хост отправляет один запрос за раз. Новые реализации возвращают явную ошибку на команды в недопустимом состоянии. Адаптеры существующих worker сохраняют задокументированную идемпотентность. При таймауте хост завершает зависший процесс, помечает текущий результат как незавершённый и при следующем запросе поднимает новый worker. Завершённость результата определяется успешным ответом IPC.

### Голос и референс в разных сервисах

- **RVC.** Голос состоит из весов конвертера и опционального FAISS-индекса. При запуске хост указывает их явно. Специфичная для RVC команда `set_voice` заменяет эти артефакты на том же устройстве, сохраняя HuBERT и RMVPE в памяти. При ошибке остаётся прежний рабочий голос. После успеха worker возвращается в `loaded` и требует `warmup`.
- **Fish Speech и F5‑TTS.** Голосовой референс может поступать прямо в `infer` вместе с текстом для синтеза. Запрос явно передаёт дескриптор WAV и текст референса, когда он нужен модели. Worker может дополнительно поддерживать заранее подготовленные референсы. При использовании такого референса запрос передаёт его идентификатор. Референс каждого запроса задаётся явно. Подготовка нового референса не меняет загруженные веса и состояние `ready`. Ошибка референса завершает только текущий запрос.
- **GigaAM, Beat This! и Dettato.** Принимают аудио для анализа. Команды и поля для установки голоса в их контракты не входят.

При кэшировании TTS-референса ключ включает ревизию модели, содержимое референса и параметры обработки. При смене ревизии или `unload` записи старой модели исключаются. Общий lifecycle управляет загруженной моделью, а работа с голосом определяется контрактом конкретного сервиса.

В Windows-сборках этой миграции TTS v1 принимает `text` и `reference` с дескриптором WAV. Fish Speech требует `reference_text` и явный `max_new_tokens`. F5‑TTS принимает `steps` и `seed` в запросе. Русский F5‑TTS требует `reference_text`, а cross-lingual использует отдельные веса предсказателя темпа. Оба worker возвращают WAV и частоту дискретизации. Первая матрица TTS собирает CUDA/WGPU, приёмка TensorRT ведётся отдельно.

### Обмен результатами

- Небольшие структурированные данные, например текст, временные метки и параметры генерации, передаются в JSON.
- Бинарный вход передаётся дескриптором `{file_name,size_bytes,sha256}` из корня обмена. Worker проверяет одно имя файла, лимит, размер и SHA‑256, затем обрабатывает проверенные байты. Пользовательское имя или произвольный путь из запроса не становятся путём на диске. Модельные пути в командах конфигурации проходят отдельную проверку.
- Worker пишет результаты под уникальными именами, исключает перезапись и возвращает дескрипторы только после успешного завершения всего запроса. Хост проверяет корень, размер и SHA‑256 каждого файла перед использованием. Для нескольких артефактов каждый элемент результата имеет собственную роль и дескриптор.

## 4. Адаптеры моделей

| Модель | Что перенести или подключить | Критерий проверки |
| --- | --- | --- |
| **RVC** | Взять `rvc-worker` из `fd6b1a9b` как эталон. PCM WAV → преобразованный WAV. Отдельные роли для весов голоса, HuBERT, RMVPE и опционального FAISS. | Два запроса с одним голосом, смена голоса с индексом и без него, отказ при плохом пути с сохранением старого голоса. |
| **GigaAM** | Адаптировать имеющийся ASR worker. Объявлять CTC и RNN‑T по семействам, включая E2E-варианты с обязательным токенизатором. Сохранять текст и доступные таймкоды. | Отдельная приёмка официальных весов для каждого публикуемого семейства. Прогон CTC не подтверждает RNN‑T. |
| **Beat This!** | Один worker для Small1 и Final1. Хост выбирает зарегистрированную модель и её веса при запуске. Сохранить Beats v1 и совместимость действующего пакета Small1. Аудио → временные метки битов и даунбитов. | Проверить реальные веса Small1 и Final1, по два файла за одну загрузку каждого варианта, сверку меток и запуск опубликованного клиента. |
| **Fish Speech 1.5** | TTS worker с текстом и референсом в запросе. Подготовленный референс — дополнительная возможность. Явные артефакты семантической модели и Firefly, роли кодировщика и декодировщика. Объявлять CUDA, WGPU и TensorRT по результатам отдельной приёмки. | Два текста с одним референсом, смена референса между запросами, одинаковые заданные параметры генерации и проверка тембра и просодии. |
| **F5‑TTS** | TTS worker с явными DiT, Vocos, словарём и референсом. Русский и cross-lingual checkpoints — разные модели. Число шагов — явный параметр. Существующий потоковый режим требует отдельного согласования DTO. | Прогон обеих моделей с одинаковым референсом и зафиксированными настройками. CUDA FP16 и TensorRT RTX проверяются отдельно. |
| **Dettato** | Аудио → MIDI. Явные пары config/weights для Transcriber, Evidence, Grouper и Drums. Сервисный запрос выбирает общий файл или отдельные MIDI, ответ содержит имена дорожек и дескрипторы файлов. | Полный музыкальный трек, совпадение нот и тайминга общего и отдельных MIDI, корректная передача ударных и исходной частоты дискретизации. |

Исходные реализации и контракты: [Beat This!](models/beat_this/distribution.json), [GigaAM](https://github.com/Atm4x/Vendor-for-burn/blob/74576d6f3d2cdf626db330781824a4f448c99370/models/gigaam/IPC_STDIO_WORKER.md), [RVC PR #2](https://github.com/Atm4x/Vendor-for-burn/pull/2). Локальные ориентиры для портов — Fish Speech `5198c695`, F5‑TTS `98f335b0`, Dettato `214f9132` плюс отдельная рабочая правка `--output-dir`. Перед интеграцией закрепить точную ревизию, включающую нужные исправления.

## 5. Порядок миграции и приёмка

1. Зафиксировать транспорт и тестовый стенд по RVC. Сохранить отдельные схемы результатов сервисов. Пройти сквозной тест RVC с реальными весами через клиент Core.
2. Подключить Beat This! и GigaAM через адаптеры существующих контрактов. Проверить, что опубликованные варианты продолжают запускаться. Публиковать новые возможности только после проверки соответствующих реально собранных пакетов.
3. Добавить TTS-адаптеры Fish Speech и F5‑TTS. Затем подключить Dettato с многопайловым результатом. В каждом PR закрепить SHA движка, тестовую конфигурацию и версию DTO.
4. Для каждого варианта пройти lifecycle, повторный тёплый запуск, ошибку веса, плохой GPU или DLL, повреждённый вход, таймаут и восстановление. Где есть смена профиля, проверить неудачную смену и повторный инференс со старым профилем. Для WGPU на AMD отдельно записать результаты с реального AMD-адаптера.
5. Прогнать сравнение с исходной реализацией на одинаковых файлах и настройках. Записать время запуска, загрузки, прогрева и тёплого инференса, а также пиковую память. Согласовать допустимое отклонение для модели до публикации. Смена транспортного слоя сама по себе не подтверждает качество или ускорение модели.
6. Собрать и проверить общий Windows-релиз по правилам ниже. Приёмка завершается установкой комплекта через Core и запуском каждой модели вне каталога разработки без сетевого доступа.

## 6. Единый релиз комплекта и Windows CI

### Версия и состав

- Один утверждённый Git-тег, например `native-workers-v1.2.0`, соответствует одному GitHub Release. В одном выпуске присутствуют RVC, GigaAM, Beat This!, Fish Speech, F5‑TTS и Dettato. Первая обязательная платформа — Windows x64.
- Установщик читает один подписанный индекс выпуска. Общая версия комплекта, например `1.2.0`, совпадает с `package_version` всех пакетов этого выпуска. Идентификаторы моделей, backends, версии IPC и DTO и SHA исходников остаются явными и могут различаться. Смена голосового референса и RVC `set_voice` не влияют на версию комплекта.
- Имя пакета: `<семейство>_v<версия>_win_x86_64.<exe|zip>`, например `gigaam-v3_v1.0.0_win_x86_64.zip`. Один пакет может содержать общий worker для CTC/RNN‑T или Small1/Final1. Варианты весов и параметры запуска задаются в манифесте. Суффикс backend нужен только при наличии отдельных бинарных сборок.
- Самодостаточный пакет можно опубликовать как EXE. Если нужны DLL, манифест или другие файлы, опубликовать один ZIP с ними и EXE внутри. Общий подписанный индекс выпуска перечисляет пакеты и их SHA‑256. Веса с ограничениями на распространение задаются как проверяемые внешние артефакты.
- Установщик выбирает доступные пакеты из одного индекса и сверяет версию, подпись и хеши до активации. Установленная ревизия остаётся пригодной к запуску при неудачном обновлении. Повторная публикация той же версии с другими байтами запрещена.

### Сборка, проверка и публикация

1. Для каждого нового worker добавить Windows job, интегрировать модель и workflow в `main` и запустить сборку с `main`. Готовые пакеты доступны как артефакты Actions по мере интеграции. Linux в эту поставку не входит.
2. На Windows x64 использовать [общую матрицу](.github/workflows/build-native-workers-windows.yml) по семейству и варианту сборки. Закрепить Rust/MSVC, нужные SDK и версии внешних библиотек для каждой строки. Публикация общего релиза запускается по утверждённому тегу после появления всех обязательных пакетов.
3. Проверки GPU проводить на Windows-раннерах с нужным физическим GPU и установленным драйвером. CUDA и TensorRT требуют NVIDIA. Для выпуска WGPU с заявленной поддержкой AMD нужна отдельная проверка на AMD. Успешная компиляция GPU-варианта на обычном Windows-раннере подтверждает сборку. Для публикации варианта обязателен также успешный smoke inference на соответствующем устройстве.
4. Этап публикации сверяет состав со списком обязательных моделей и вариантов, совпадение версий, manifest/ZIP, хеши и результаты тестов. При отсутствии любой обязательной сборки выпуск остаётся закрытым. Сначала загрузить все ассеты и подписанный индекс в черновик GitHub Release, затем открыть его одним действием. Только после этого установщик может увидеть новую версию.
5. Текущий отдельный релиз Beat This! использовать как источник шагов сборки и как совместимый канал для уже выпущенных версий. Публикацию общего комплекта выполняет только общий workflow. Критерий готовности — одна версия в установщике, все шесть моделей в каталоге, установка отдельных выбранных пакетов и успешный запуск каждой модели из этой версии.
