# Stage 111 — NSF Phase GEMM architectural replacement

## Evidence and conclusion

Stage110 NCU (RTX4060, 2026-11-15): for stride10, ILP4 vs tile2, CUDA CTA count 320 vs 160; L1/TEX LSU throughput 72.6% vs 75.4%; FMA pipe 34.3% vs 18.1%; Long Scoreboard 6.48 vs 15.93; compute time ~105 vs ~170 μs. Doubling per-thread channel work provably reduced latency hiding. Stage97 whole-RVC PyTorch NSYS shows a substantial fraction of convolution kernel time spent in `cutlass_tensorop_f16` cuDNN kernels. This is FP16 Tensor Core execution, not the same FP32 arithmetic implementation as Stage106–110. The trace does not establish that exact Stage110 ConvTranspose1d shapes were handled by those kernels, hence the matched PyTorch benchmark is mandatory.

For common NSF stride10: N2, Cin128, Cout64, Tin256, K20, pad5, the polyphase reduction length is 256 and the time dimension is 256. There are 10 phase matrices, each size [256,256] @ [256,64] per batch. The convolution executes about 83.89 million FMAs. The explicit gather staging contains 1,310,720 scalar elements (2,621,440 bytes = 2.50 MiB at FP16). This is an upper-bounded, sequentially addressed staging buffer. It eliminates many per-output GPU load instructions in exchange for two linear staging kernels and dispatch costs. Whether the tradeoff pays off must be measured.

## Decision gates

1. **Correctness:** F32 max_abs <=1e-4 against existing Direct; F16 max_abs <=5e-3 and SNR >=50 dB against F32; verify full RVC PCM/SNR separately.
2. **Matched cost:** record full synchronized host ms including gather/matmul/scatter and casting, not only matmul kernel. Compare F16 PyTorch at same dimensions separately, not to F32 direct as if equivalent precision.
3. **GPU architecture:** check actual Tensor Core utilization in NCU report for the matmul kernel; if zero, inspect cubek-matmul precision selection and scheduling rather than tuning another scalar-FP32 kernel.
4. **Memory:** account for phase input buffer size, weight-packing only at model initialization, output layout and any implicit backend copies.
5. **Production:** unset `RVC_NSF_PHASE_GEMM` until both numerical and performance gates are closed. If Phase GEMM is slower, do not promote it.

## CUDA precision correction (2026-11-15)

RTX4060 user execution failed the strict FP32 phase GEMM gate on `upsample8`: max_abs `0.00013528811`, SNR `58.48 dB`. The original CubeCL matmul selected accelerated `f32 -> TF32` operand staging (`cubek-matmul` `adjust_dtypes`), reducing operand precision before Tensor Core accumulation. The earlier CPU geometry reference tested only the phase algebra and could not reveal this backend precision policy.

The corrected `phase_f32` path uses three accelerated TF32 matmuls: `Xhi * Whi`, `Xhi * Wlo`, and `Xlo * Whi`. High and residual weight matrices are prepacked once at model initialization. Each inference constructs one phase input matrix, splits its high/residual components on GPU, and combines all three results with bias directly in scatter. Neglected `Xlo * Wlo` is second-order in the TF32 residual. FP16 remains the independently gated experimental path.

Standalone CPU tests reproduce high-high TF32 max_abs above `1e-4` for K256 and verify compensated error below `1e-5` on the same synthetic family. Type checks confirm the CubeCL API; only a fresh Windows CUDA execution can establish end-to-end FP32 parity and speed. Runner now checks all modes before starting the costly multi-pass NCU capture, failing fast if any CUDA JIT/path fails.

The correction incurs two extra matmuls and input splitting relative to the previous approximate phase GEMM. It is not yet proven faster than the optimized polyphase ILP4. Do not enable it in production without verifying both accuracy and latency.
