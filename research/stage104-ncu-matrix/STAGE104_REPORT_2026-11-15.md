# Stage 104 — full RVC Nsight Compute profiling matrix

Date: 2026-11-15. Repository: `Atm4x/Vendor-for-burn` / PR #2. Based on Stage103 (`b8a8a29dca143e30437cc3c5d403e1f6bb02285f`).

## Motivation and measured evidence

Stage102 RTX 4060 Direct FP32 Conv2d captured **456.42 us**, GPU **SM compute 9.04%**, memory throughput **95.32%**, L1/TEX active throughput **99.58%**, DRAM **4.66%**, L2 **1.85%**, L1 hit rate **97.08%**, 48 registers/thread, zero dynamic shared memory, 72.92% achieved occupancy. A kernel can be constrained by L1/TEX wavefront issuance despite low DRAM utilization. These measurements apply to **one captured direct Conv2d**, not the whole RMVPE model. Stage102 matched CUDA call times showed Rust/PyTorch FP32 differences of 7.94× and 5.68× for two dense 3×3 cases; these numbers include host/API and synchronization overhead.

Stage103 adds an experimental register-reuse Conv2d; the next question is how its GPU kernel differs in L1/TEX, occupancy, register pressure, and actual latency, as well as the cost of **other major RVC blocks**. Stage104 introduces no new numerical approximation or default inference routing.

## New instrumentation

### 12 matched micro-CUDA targets

For each of `dense3x3`, `dense3x3_wide`, `pointwise1x1`, `depthwise3x3`:
- Burn Direct FP32 NCHW;
- Burn register-reuse FP32 NCHW (only dense 3×3 uses the new kernel; other shapes fall back to Direct);
- PyTorch `F.conv2d` FP32 NCHW, TF32 disabled.

The existing Stage103 Rust binary now accepts optional third positional argument `[case|all]`; one named case produces the NVTX push/pop range `stage104_conv2d_<case>`. Full output parity is verified for eligible reuse kernels. PyTorch probes use matching deterministic inputs/weights, one case per capture, and do not modify the upstream repository.

### 17 RVC block ranges

Top-level: `audio_h2d`, `hubert`, `hubert_readback`, `rmvpe`, `retrieval_pitch`, `encoder`, `latent`, `flow`, `nsf_prepare`, `nsf`, `nsf_readback`.

Subblocks: `rmvpe_unet`, `rmvpe_gru`, `rmvpe_head`, `nsf_upsample`, `nsf_noise_conv`, `nsf_residuals`.

New marks are opt-in (`RVC_NVTX=1`), non-invasive, and preserve all previous algorithm choices. Full-model NCU captures are constrained to the **warmed** `stage102_rust_measured` parent and named child/subblock, with `--nvtx-push-pop-scope process`. All blocks are available separately through `-Blocks`. `no_kernels` is a valid explicit outcome for CPU-only/empty ranges, not a speed claim.

### Kernel families and NCU metric sets

`-Families all,conv,gemm,recurrent,elementwise`; a family filter is applied only when requested. Default `all` does **not** hard-code kernel names and may spend launch slots on tensor copies. For in-depth hardware counters, run a second narrow capture with `-Families conv` and the desired block.

Balanced sections: `SpeedOfLight`, `LaunchStats`, `Occupancy`, `MemoryWorkloadAnalysis`, `ComputeWorkloadAnalysis`, `WarpStateStats`, `SchedulerStats`. Full: NCU `--set full` (much slower). Target count is capped at 60 by default; no unbounded replay. `-NcuLaunchCount` bounds captured kernels per target. `-IncludeNsys` optionally captures a broad timeline per distinct strategy.

## Output and safety contracts

- Runner: `Run-RVC-Stage104-NCU-Matrix.ps1`.
- Results: `RVC_STAGE104_NCU_MATRIX_RESULTS.zip`, containing ONLY NCU/optional NSYS reports, JSONs, and logs.
- Temporary WAVs and output audio remain outside archived reports and are deleted after execution. No model, HuBERT, RMVPE or FAISS index is packed.
- NCU CLI CSV export is omitted: a previous version emitted `bad conversion` for a valid 2025.1.0 `.ncu-rep`. Use the NCU GUI to inspect/export metrics.
- NCU zero-kernel results from micro targets cause failure; GPU-empty full pipeline ranges are recorded as `no_kernels`. No success ZIP if every capture is empty or the run fails.
- Each execution has its own unique report directory; old `.ncu-rep` files cannot be mistaken for new captures.
- Uninstrumented latency and NCU-replay wall times are recorded separately; never compare the latter to production inference latency.
