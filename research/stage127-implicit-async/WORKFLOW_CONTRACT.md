# RVC / Burn / CubeCL — неизменяемый протокол совместной R&D-работы

**Редакция:** 2026-11-17  
**Статус:** рабочий контракт пользователя для следующих циклов R&D.  
**Репозиторий:** `Atm4x/Vendor-for-burn`, PR #2, ветка `experiment/conv-kernel-rnd-stage33-20261110` (пока пользователь не укажет иное).

> Не переизобретать формат исполнения, поставки, анализа и профилирования на каждом Stage. Изменение этого протокола — **только по явному запросу пользователя**. Наличие новой идеи или удобство агента не является разрешением менять процесс.

## 1. Цель R&D и источник истины

1. Оптимизируется **реальный RVC GeneratorNSF / полный RVC-путь в Rust, Burn и CubeCL**, с приоритетом RTX 4060/CUDA, но по возможности в общем CubeCL-коде для других бэкендов.
2. Python/PyTorch CUDA — **референс корректности и скорости**, а не объект оптимизации. Нельзя переключать разработку на PyTorch FFT/GEMM-прототипы вместо Rust/CubeCL без явного согласования.
3. **NSYS полного пути** задаёт реальные горячие зоны, последовательность запусков, синхронизации, простаивания, CUDA streams и корреляцию CPU API → GPU kernel. Суммарные таблицы `nsys stats` допустимы только как вспомогательное ранжирование; они **не заменяют timeline**. Для глубокого анализа сохраняются `.nsys-rep` и по необходимости экспорт SQLite с отдельными событиями.
4. **NCU конкретного CUDA-kernel** определяет узкое место. Использовать настоящие счётчики (задержки/warp stall, L1/TEX, L2, DRAM, FP32/FMA/Tensor pipe, occupancy, регистры, spills, grid/block) и их контекст. Нельзя выводить bottleneck по одному только MAC, названию алгоритма, occupancy или итоговому времени.
5. Анализировать **все уже выданные пользователем данные**: исходные `.ncu-rep`, `.nsys-rep`, `exported_csv/*.csv`, JSON, логи и сопроводительные ZIP. **Перед просьбой о новом профиле или экспорте сначала проверить библиотеку и вложения.** Если существующий экспорт содержит посторонние/нецелевые ядра — явно об этом сообщить и объяснить, какие измерения не покрыты.
6. Чётко разделять: *наблюдение измерения* → *вывод об ограничении* → *гипотеза алгоритма* → *эксперимент* → *подтверждённый выигрыш*. Не объявлять оптимизацию выигрышной, пока не прошли аппаратный A/B и численная приёмка.
7. Сравнивать **сопоставимые** shapes, точности, модели, WAV, входы, GPU, число запусков и режимы GRU. Отдельно фиксировать GPU kernel time (NSYS), NCU replay (не использовать вместо обычного времени), warm median, cold time, сквозную латентность, упаковку данных и запусков CUDA. Переменные окружения и порядок A/B должны быть явными; по возможности ABBA / повторные циклы.
8. Предпочтение математически и архитектурно оправданной переработке всего участка, а не бесконечному добавлению `tileN`, `fused X+Y`, нового GEMM или перераскладке без данных. Негативные результаты предыдущих Stage учитывать, не реанимировать их как новые идеи без новых фактов.

## 2. Строгий порядок ОДНОГО цикла оптимизации

**Этап A — аудит входов и существующего GPU-профиля.** Получить актуальное состояние **только из git bundle** (через имеющийся Git Bridge CI) и локальных source-only артефактов. Исследовать архивы предыдущих измерений, называть проверенные данные и ограничения. Не использовать множество GitHub GET/clone для исходников. GitHub-коннектор — для commit, веток, CI и получения bundle, а не замена локальной работе.

**Этап B — доказанный bottleneck.** По NSYS найти дорогостоящий участок *полного графа*. По NCU определить конкретный ограничивающий аппаратный ресурс. Сформулировать проверяемый механизм, ожидаемый выигрыш, риск регистров/памяти/точности, альтернативы. Если NCU-фактов недостаточно, **не внедрять наугад**, а извлечь имеющиеся метрики либо поставить минимально необходимый профилирующий эксперимент (без самовольной пересборки).

**Этап C — локальное изменение Rust/CubeCL.** Только если теория опирается на измерение: менять оптимизируемые исходники, при необходимости всю архитектуру свёрток в Burn/CubeCL. Основные режимы и эталон сохранять для A/B. Не трогать неиспользуемые Legacy/Obsolete-скрипты. Изменения проводить локально на рабочем дереве из bundle.

**Этап D — локальные проверки.** Rust 1.100.0, офлайн checks, математические reference-тесты, проверки контрактов и компиляция доступных features (`cpu,cuda,wgpu` по применимости); внимательно отделять `cargo check` от реального CUDA JIT/GPU. Не выдавать результаты CI Windows без RTX 4060 за аппаратное доказательство. Для Unity не выполнять `dotnet build`.

**Этап E — ЕДИНСТВЕННАЯ публикация после законченного Rust-цикла.** После содержательного изменения Rust/CubeCL и локальной проверки **один связный push через GitHub-коннектор**, единожды актуализировать *ОДИН* действующий Windows CI workflow для Stage NNN, упаковать EXE + нужные рабочие скрипты + README + manifest в один ZIP/Actions artifact. Выключить ненужные автоматические старые Stage workflow (сохраняя историю/legacy-исходники и Git Bridge). Не запускать 2–10 параллельных старых CI на одну поправку.

**Этап F — GPU-приёмка.** Пользователь скачивает **один CI artifact** с EXE и всеми PS1/Python-скриптами уже внутри. Агент выдаёт **одну проверенную основную команду** с нужными параметрами и, если нужно, отдельную диагностическую. Пользователь возвращает один ZIP результатов, без моделей/WAV. Агент анализирует результаты прежде, чем начинать следующий цикл. Если тест выявил баг, можно передать полную исправленную PS1 локально без создания CI — **не обновлять CI из-за одной PS1**.

## 3. Публикации, скрипты, CI — жёсткие запреты

- **НЕТ изменения Rust/CubeCL → НЕТ правок GitHub CI, workflow и пуша PS1 через CI.** Исправления вспомогательной PowerShell-сценария — не повод пересобирать весь Rust/Windows.
- **НЕТ нескольких промежуточных пакетов за один Stage.** Один понятный пакет от одного CI после завершения цикла. Отдельные одноразовые ссылки чата не должны быть обязательными: они могут исчезать, поэтому рабочие скрипты **всегда включены в CI ZIP** соответствующего Stage.
- Новый **Stage NNN** содержит собственный **актуальный** PS1, необходимые вспомогательные скрипты, правильные параметры и версию EXE. Не ссылаться на старый Stage116 PS1 как на обязательную зависимость, если он не включён в пакет.
- Нельзя тихо менять имена параметров, формат итогового ZIP, `embed/`, исполняемый файл, расположение профилей, runtime, переменные окружения или source-of-truth. Любое необходимое изменение отмечать в README/manifest и предупреждать пользователя.
- Статические PowerShell syntax checks и dry-run перед публикацией обязательны; сетевая компиляция ради синтаксиса PS1 запрещена.
- Ни в GitHub Actions artifact, ни в пользовательском ZIP результатов **не должно быть** WAV/FLAC/MP3, моделей `.pth/.pt/.onnx`, `.index`, приватных весов. Разрешены метрики, CSV/SQLite, NCU/NSYS-профили, короткие логи, JSON, `BUILD_STATUS`, `README`, EXE и скрипты в CI-артефакте.
- Профайлер запускается из известных путей; не устанавливать автоматически NVIDIA runtime, CUDA, Nsight или Python и не скачивать DLL. При ошибках давать точную диагностику.
- Недостатки интерфейса и ошибки PS1 исправлять в скрипте и тестировать без перепаковки Rust; **при следующем настоящем Rust-изменении включить все накопленные исправления в единый Stage CI ZIP**.

## 4. Зафиксированные Windows пути пользователя

Единственный основной Python, содержащий PyTorch CUDA, который использовать в командах RVC:

```text
D:\Projects\tts-with-rvc\.venv\Scripts\python.exe
```

**Не заменять его** на `miniconda3/envs/torch2.6.0/python.exe`: путь Conda ниже относится только к наличию legacy DLL.

```text
CUDA_PATH       = C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v12.8
CUDA_PATH_V12_4 = C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v12.4

NCU 2025.1  = C:\Program Files\NVIDIA Corporation\Nsight Compute 2025.1.0\target\windows-desktop-win7-x64\ncu.exe
NSYS 2024.6.2 = C:\Program Files\NVIDIA Corporation\Nsight Systems 2024.6.2\target-windows-x64\nsys.exe
NVTX v2 DLL = C:\Users\mrtak\miniconda3\envs\torch2.6.0\Lib\site-packages\torch\lib\nvToolsExt64_1.dll
```

Другие обнаруженные NSYS (не выбирать автоматически, если задан путь выше):

```text
C:\Program Files\NVIDIA Corporation\Nsight Systems 2023.4.4\target-windows-x64\nsys.exe
C:\Program Files\NVIDIA Corporation\Nsight Compute 2025.1.0\host\target-windows-x64\nsys.exe
```

- Профилирование NSYS: использовать проверенные `--trace=cuda,nvtx`; **не добавлять `osrt` без проверки поддержки конкретной версии**.
- NVTX: подключать найденный каталог DLL к `PATH` текущего процесса, проверять статус до NCU; отсутствие NVTX не должно незаметно менять целевой NCU профиль на нерелевантный нефильтрованный захват. Если NVTX scope из-за асинхронного исполнения не совпадает с CUDA-ядром, выбрать `--kernel-name` и проверенный `--launch-skip`/геометрию.
- У пользователя модель/индекс/WAV уже могут лежать в `embed/` рядом с извлечённым CI; не включать их в поставку и не изобретать новые пути.

## 5. Доказательства, уже присутствующие в R&D

- Stage116: полноценный WAV, `baseline_ntc` побитово совпал с `baseline`; `transport` и `transport_ntc` совпадают друг с другом, максимум 1 PCM LSB отличия от baseline (260 из 119200 сэмплов, ~96.17 dB SNR для одного тестового WAV). Нельзя экстраполировать качество на все записи без проверки.
- Stage118: NSYS полный timeline показал ускорение Conv1d ResBlocks примерно в 6 раз относительно baseline по GPU-времени, но за пределами NSF есть значимые другие участки (включая RMVPE GRU/HuBERT). Не сводить полное ускорение к ResBlock.
- Stage119: tile4 против tile2 даёт около 2.45% выигрыша полного прогона с текущими контрольными данными; это **не доказательство причинно-аппаратного bottleneck**, и не сигнал безусловно наращивать tile.
- Архив **Stage116** `20261116T195206Z.zip` уже содержит `exported_csv/` с двумя NCU CSV (по 6 запусков каждый). Один capture включает baseline `direct_conv2d` с посторонними вспомогательными kernels; другой — в основном вспомогательные операции transport. Эти файлы были переданы ранее, и агент обязан их анализировать, но не ошибочно объявлять корректной профильной парой ResBlock.
- **Stage117** `resblock-kernels.csv` (2 ядра, 1679 столбцов): оба ядра `preact_residual_temporal_kernel`, регистры 39/40, L1/TEX throughput ~53.1/52.4%, L2 throughput ~24.3/24.1%, FMA pipe active ~39.3/38.8%, Tensor pipe 0%; есть `Long Scoreboard` 4.36/4.81 и `Math Pipe Throttle` 2.46/2.39 (*average stalled warps per issued instruction*, не проценты), LG throttle ~0.05/0.04. Время NCU-replay ~8.05/9.70 мс, **не сравнивать напрямую с NSYS non-instrumented временем**. Диагноз следующего алгоритма должен учитывать **все** эти счётчики, а не один пик.

## 6. Обязательный формат передачи результата каждого цикла

В завершении Stage NNN агент сообщает:

1. **Какой bottleneck доказан** (конкретные NCU метрики + NSYS место в полном графе; если не доказан — прямо так написать).
2. **Какой алгоритм внедрён и почему** (исходная причина, проверяемая гипотеза, ожидаемые tradeoffs), только если реально сделано изменение Rust/CubeCL.
3. **Что локально проверено** — список фактов, а не обещаний. Чётко помечать `CHECK`, `GPU unverified`, `quality PASS/FAIL`.
4. **Один опубликованный GitHub commit/PR + один Actions run + один Windows artifact** — только по завершении цикла изменения Rust/CubeCL.
5. **Одна команда запуска из этого же CI ZIP** и формат одного архивируемого отчёта. Если опубликованного ZIP нет — не выдавать временные ссылки чата за устойчивую доставку.
6. **Чего данные ещё не подтверждают**, чтобы не выдавать теорию за измерение.

## 7. Ограничение долговременной памяти

Этот MD — явное долговечное описание пользовательских правил. Он не доказывает, что правила автоматически записаны во внутреннюю память ChatGPT. В этой сессии инструмент прямой записи туда недоступен; пользователь может добавить текст документа в **Settings → Personalization → Memory summary → Manage**, если желает зафиксировать правила между независимыми чатами. Агент не должен утверждать «записал в память» без подтверждения системы.

**Краткое правило:** сначала полный анализ имеющихся NCU/NSYS → доказанный bottleneck → один цикл Rust/CubeCL → тесты → ОДИН push/один CI/один Stage ZIP со ВСЕМИ скриптами → GPU результаты → новый цикл. Ни отдельного CI ради PS1, ни новой архитектуры наобум, ни смены Python/CLI без согласования.
