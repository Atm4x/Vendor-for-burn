# Stage 50 — RTX 4060 integrated NSF CUDA A/B

**Дата анализа:** 11 ноября 2026. **Источник:** загруженный пользователем `NSF_INTEGRATED_STAGE50_RESULTS.zip` (запись файлов 11 ноября 2026, около 00:38 по времени системы источника).

**Репозиторий:** `Atm4x/Vendor-for-burn`; экспериментальный PR #2, ветка `experiment/conv-kernel-rnd-stage33-20261110`.  **Исходный интеграционный коммит:** `6abdf28c3c04e1ec93c45837850408083f094128`.

## Краткий вывод

1. **Интеграция полного NSF на CUDA работоспособна в рамках синтетического checkpoint**: все 6 вариантов, в 2 циклах на 3 длинах, завершились; **36/36 полных FP32-буферов совпадают побитово** с Baseline для соответствующего размера, `max_abs_error = 0`. Это подтверждено дополнительной проверкой бинарных файлов из архива, независимо от `summary.json`.
2. **Самый быстрый из испытанных вариантов по среднему двух process-level медиан на всех трёх длинах — `Sequential + Stage49 Prepacked`**, а не Packed/Quad/QuadInterior. Его выигрыш относительно исходного Parallel+Direct составил **2,80× (64), 2,00× (256), 1,85× (1024)**.
3. **Stage50 Packed/Quad/QuadInterior успешно подключены к полному NSF, но их дополнительный выигрыш относительно Stage49 Prepacked в этом CUDA-тесте не подтверждён.** Все три варианта проигрывают Stage49 Prepacked по среднему двух медиан. Особенно нестабилен QuadInterior.
4. Ранее полученные на CPU 8–10× **не перенеслись автоматически на RTX 4060**. CPU batch=32 — отдельная CPU-настройка, не реализованная аналогичным образом в CUDA. Замеры включают Burn forward и блокирующий CPU readback, это не kernel-only GPU время.

## Условия измерений

- GPU: **NVIDIA GeForce RTX 4060** (устройство указано в пользовательском контексте предыдущих Windows-тестов; в этом ZIP нет нового `nvidia-smi` диагностического файла).
- Полный **синтетический NSF-декодер**, фиксированные входы и checkpoint, не фактическая производительность всех компонентов RVC/реальных весов CrazyMita.
- 20 измерений после 5 прогревов **для каждого варианта в каждом отдельном процессе**; два цикла: прямой порядок и обратный. Результаты в таблицах — опубликованные медианы каждого процесса, не агрегированные raw GPU events.
- Измерение `median_total_ms` включает запуск forward и синхронное чтение результата на CPU. `median_submit_ms` — host wall-clock вызова Burn/CubeCL, а не чистое GPU-время; `median_readback_ms` — задержка чтения. Медианы фаз нельзя автоматически складывать в медиану total.
- `Stage49 Prepacked` использует `RVC_CONV_WEIGHT_PREPACK=1` и обычный Burn Conv1d; `Stage50 Packed/Quad/QuadInterior` выбираются через `RVC_NSF_CONV_KERNEL` и используют **другую** предварительную физическую раскладку весов. Это альтернативные ветви, а не последовательное суммирование обеих схем упаковки.
- В архиве отсутствует трассировка числа фактических Stage50 kernel launches: PowerShell-runner специально выключает `RVC_NSF_CONV_TRACE`. Поэтому численная parity и выбор переменной окружения не заменяют runtime-доказательство, сколько раз специализированные ядра реально запускались.

## Нестабильность и интерпретация

- **64 кадра:** Stage50 Packed изменился с 1,9620 до 1,2151 мс между процессами; QuadInterior — 1,8270 → 2,0240 мс. Stage49 Prepacked в обоих процессах быстрее Stage50-ядер.
- **256 кадров:** результаты Stage49 Prepacked стабильнее: 1,1525 / 1,1345 мс. Stage50 Packed — 1,1901 / 1,1835 мс; Quad — 1,1789 / 1,2224 мс; QuadInterior — 1,1846 / 1,2167 мс. Различия внутри диапазона десятков микросекунд, и нужен более строгий GPU-event A/B перед ранжированием ядер.
- **1024 кадра:** QuadInterior сильно меняется между процессами (1,2838 и 2,5179 мс), причём второй содержит повышенное `submit` (2,0311 мс) и `readback` (0,4642 мс). Его среднее не следует трактовать как точное intrinsic kernel performance. Stage49 Prepacked: 1,2657 / 1,2375 мс; Quad: 1,3323 / 1,2917; Packed: 1,3755 / 1,3153.
- При сравнении independent-process медленных и быстрых режимов возможны изменения частоты GPU/CPU, драйверного состояния, кэша, JIT и аллокатора. Два process-level повтора недостаточны для уверенных выводов о малых различиях (2–10%).
- Наблюдаемый выигрыш Sequential и подготовленных весов существеннее различий между Stage50 convolution-ядрами, но точную долю каждого уровня в GPU execution из этого инструмента извлечь нельзя.

## Загрузка декодера

Время `load_ms` было измерено один раз на процесс; два независимых результата каждого режима, в мс. Оно исключает первоначальную загрузку файла checkpoint и создание устройства.

| Вариант | №1 | №2 |
|---|---:|---:|
| Baseline (Parallel / Direct) | 88.4573 | 83.0545 |
| Sequential / Direct | 79.3963 | 77.4123 |
| Sequential / Stage49 Prepacked | 85.3876 | 80.3805 |
| Sequential / Stage50 Packed | 84.4376 | 78.7961 |
| Sequential / Stage50 Quad | 84.8524 | 81.0215 |
| Sequential / Stage50 QuadInterior | 78.8625 | 83.2199 |

Разброс близок к различию между вариантами; **по двум запускам нет оснований утверждать экономию стоимости загрузки**. Нынешняя предварительная упаковка весов может добавлять расходы на CPU readback/GPU re-upload: в будущем стоит сравнить специализированный GPU-side pack, persistent prepared-weight lifetime и amortization за N forward.

## Что делать после Stage 50

1. **Не назначать QuadInterior по умолчанию.** При текущем синтетическом checkpoint на CUDA самый сильный кандидат — Stage49 Prepacked вместе с Sequential. Это исследовательская конфигурация, не production-рекомендация для реальных весов.
2. Подтвердить фактический dispatch: включить trace/счётчики `Direct`, `Packed`, `Quad`, `QuadInterior` на уровне Burn/CubeCL; указать число вызовов и shape каждого ядра. `preparation="baseline"` в JSON профайлера для Stage50 **не означает**, что специфическая упаковка отсутствует — это только старое поле Stage49-инструмента.
3. Выполнить interleaved A/B **в одном CUDA-процессе** на общем заранее загруженном checkpoint с отдельными persistent weight instances/streams; собирать CUDA events для kernel-only и host wall-clock отдельно. Повторить по нескольким независимым сессиям, с одинаковым steady-state.
4. Измерить настоящие NSF Conv1d-геометрии и набор длительностей, проверить, что bottleneck — свёртка, а не dispatch/CPU readback; инструментировать аллокации, materializations и веса.
5. Только затем разработать deterministic per-shape kernel selection, оптимизацию persistent layout и static weights без GPU→CPU→GPU copy. Подтвердить на CPU, WGPU, CUDA и реальных checkpoints; `main`/production NSF оставить неизменным до приемки.
